# NeoPhylo v1.4d: tree reading, design spec

Status: Draft for owner review · Date: 2026-11-18 · Repo path: `docs/superpowers/specs/2026-11-18-neophylo-v1.4d-tree-reading-design.md`
Builds on the v1–v1.4c specs. Roadmap entry: `docs/roadmap.md` § v1.4d (moved forward from v1.6).
Market check behind it: `docs/market/2026-11-18-market-and-viability.md`.

## 1. Purpose and decision record

v1.4d teaches students to **read** phylogenetic trees before they build them. It targets the
documented "tree thinking" misconceptions and opens NeoPhylo to **intro biology**, the largest market,
whose students never see a distance matrix.

**Why now (owner, 2026-11-18):** the market check found intro biology is the biggest audience,
tree reading is the work easiest to grade automatically, and research favours reading trees before
building them. The owner moved tree reading ahead of v1.5 so that outreach after v1.5 reaches
intro-biology instructors from day one. v1.5 (assessment) will grade the question types built here,
so every answer must be computable and every question must survive per-student variation.

**Decisions (owner, brainstorming 2026-11-18):**
- **Tree reading before v1.5, all of it** (option B); named v1.4d so "v1.5 = instructor-ready,
  outreach starts" stays true *(naming: conductor's call)*.
- **A separate "Reading trees" area** (option A): a simple screen with the tree(s) and the question,
  real organisms, its own lessons in the library and its own exercise type in the editor. No matrix,
  stepper or analysis panels.
- **Before/after questions are NeoPhylo's own** (option A), mapped to the published misconception
  categories and labelled "not validated"; the guide cites the published instruments.
- **Format coverage of published instruments:** every item *format* used by the published tree-thinking
  tests must be expressible in NeoPhylo without code, gradable by the engine and drawable. Proven by a
  committed set of NeoPhylo-written items that mirror each published format (§8.3). This lets an
  instructor who obtains permission type a published test into NeoPhylo.
- **All five drawing styles in v1.4d:** diagonal ("V") trees, tips at the top, lettered internal
  nodes, an optional time axis, and trait changes marked on branches.
- **Architecture: a new "reading set" file type** with a new engine module that computes every answer
  (approach 1, §3).

**Calls made by the conductor (owner may overrule while reviewing):** marked *(conductor's call)*.

**Success criteria:**
1. Every computed answer (MRCA, clade test, same-relationships test, relatedness, node order, trait
   membership) matches an independent oracle (`ape`/`phangorn`) on committed fixtures.
2. Property tests: every answer is unchanged by rotating any node and by redrawing in any style;
   relabelling taxa maps answers through the same relabelling.
3. Every format in the coverage list (§8.3) has at least one committed item that loads, renders in
   every style it allows, and is answered correctly by the engine.
4. An intro-biology student can complete every built-in reading lesson on a phone, a tablet (touch
   only), a laptop (mouse only) and with keyboard only, and with a screen reader.
5. Every built-in reading lesson has a paper worksheet and an answer key whose every answer comes from
   the engine at render time.
6. All existing engine, parity, lesson-premise and old-link tests pass unmodified. No existing number
   changes. The only existing views that change are the header (new "Reading trees" item) and the
   library (new filter and cards); their snapshot baselines are regenerated in one owner-gated PR
   *(conductor's call)*.

## 2. Scope

### 2.1 In v1.4d
- Engine: a `reading` module (§5): tree queries, item validation, answer computation, variant
  transforms (rotation, tip-order shuffle, relabelling) with no UI yet.
- Oracle fixtures from `ape`/`phangorn` (§5.6).
- Reading-set file format, schema version 1 (§4), loader, share links (`#r=`).
- Tree drawing styles (§6): rectangular and diagonal; tips right or tips up; lettered internal nodes;
  optional time axis; trait marks on branches; polytomies.
- The Reading trees area (§7): question types, tap/click/keyboard interaction, practice feedback.
- Editor reading mode (§7.5).
- Content (§8): four reading lessons, two parallel before/after forms, the format-coverage set.
- Library cards, paper worksheets and answer keys for reading sets; an instructor-guide section and a
  50-minute tree-reading class plan (§8.4).

### 2.2 Non-goals
- Per-student variants in the UI, graded mode, completion codes, bulk grading (v1.5). v1.4d ships
  the engine's variant transforms only, tested but not exposed.
- Unrooted (radial) trees (v1.8 drawing work). The published intro instruments' answerable items use
  rooted trees *(conductor's call)*. Rooted circular trees are in scope (§6).
- Organism images or silhouettes: names only, no image licensing *(conductor's call)*.
- Building trees from data in the reading area; links between reading sets and sandbox exercises
  beyond a "Next: how trees are built" pointer in the library.
- Shipping any published instrument's items, wording or figures.
- Hiding answers for real (no accounts; v3.0).
- Changes to existing lessons, labs, the sandbox tree view or exports.

## 3. Approaches considered

1. **A new "reading set" file type with an engine module that computes answers** *(chosen)*. Each
   item holds one or more trees, a drawing style and a question type; the engine computes every
   answer and refuses broken items. Reuses the library, link, worksheet and print plumbing. Makes
   v1.5 variants nearly free: rotate, reshuffle, relabel, recompute.
2. **Extend the exercise format (v6) with tree-only data and new prompt types.** Reuses the loader
   directly but bends a step-based format (prompts attached to NJ joins) around step-less questions,
   and risks existing lessons and the old-link corpora. Rejected.
3. **A generic quiz engine with tree pictures and typed-in answers.** Fastest and can mimic any test,
   but answers are not computed (breaks "science lives in Rust" and engine-computed keys) and v1.5
   could not vary trees. Rejected.

## 4. Reading-set format

### 4.1 File
A reading set is JSON validated by `exercises/reading.schema.json`:

- `schema_version: 1`, `kind: "reading"`, `id`, `title`, `summary`, `meta` (level, minutes,
  objectives, as v1.4c lesson metadata).
- `taxa_pool` (optional): named lists of substitute organisms for relabelling variants (used by v1.5).
- `trees`: named trees, each `{ newick, node_letters?, times?, marks? }`:
  - `newick`: rooted; polytomies allowed; branch lengths optional; internal node labels allowed.
  - `node_letters`: map from a node (identified by its tip set, §4.2) to a display letter.
  - `times`: node ages for a time axis (each node identified by tip set), with `unit` and an
    optional `source` citation; ages must decrease from root to tips. Or `"times": "schematic"`
    (axis shows direction of time only, no numbers).
  - `marks`: trait changes `{ on: <clade>, trait: "<name>", change: "gain" | "loss" }`, placed on the
    branch leading to that clade.
  - `traits` (optional): per trait, display names for the ancestral (root) and derived states
    (e.g. "no hair" / "hair"); without it, states are shown as "lacks T" / "has T".
  - `points` (optional): lettered points on branches or tips (a branch is named by the clade below it),
    used as answer options by `mrca` and `place_taxon`.
- `items`: ordered questions (§4.3), each with `text`, optional `note_after` (shown after answering),
  `style` overrides, and type-specific fields.

### 4.2 Identifying nodes and branches
Nodes and branches are identified by **the set of tips below them** (a clade), never by position or
Newick order, so identifiers survive rotation, restyling and variants. The root is `"root"`. An
identifier that names no node of that tree is a validation error.

### 4.3 Question types
Every type except `concept` and the reason part of `two_tier` has an engine-computed answer.

| Type | Student does | Engine answer |
|---|---|---|
| `which_differs` | Picks which of 2–4 trees shows different relationships, or "all show the same" (2 trees = "same relationships? yes/no"); the trees may be drawn in different styles. Variant: given a larger reference tree, which smaller tree conflicts with it | Rooted clade-set comparison; for the reference variant, the reference restricted to each candidate's tips is compared. Refused unless the answer is unique |
| `which_fits` | Given 2–4 small rooted trees, picks which large tree agrees with all of them | Each candidate restricted to each small tree's tips must match it; refused unless the answer is unique |
| `mrca` | Taps the most recent common ancestor of highlighted tips. Options may be lettered points on nodes, on branches or on tips | MRCA node; points elsewhere are wrong |
| `place_taxon` | Given "X is the sister of {set}", taps the lettered branch point where X would attach | The stem branch of the clade of the set's MRCA |
| `is_clade` | Says whether highlighted tips form a clade; or, for a group defined by a trait, whether it is monophyletic, paraphyletic or polyphyletic | Monophyly test. Three-way rule for trait-defined groups: monophyletic if the group is exactly a clade; paraphyletic if the trait arose once (one gain) and the group is that clade minus descendants that lost it or were excluded; polyphyletic if the trait arose more than once (several gains) *(conductor's call: bare tip sets get only clade / not a clade, because para vs poly is not defined by tips alone)* |
| `count_clades` | "How many clades are in this tree?" | Number of internal nodes including the root; single tips not counted; the convention is printed in the item *(conductor's call)* |
| `smallest_clade` | Taps or selects the smallest clade containing given tips | Clade = tips under the MRCA |
| `closest_relative` | "Which is A's closest relative?" (single or select-all), "Which is most distant from A?", or "Is A closer to B or to C?" with an "equally close" option | Closest: all tips in A's sister group. Most distant: all tips outside the root child that holds A (or, for a labelled node, the tips outside it). Pairwise: compares MRCA depths; ties (polytomy, or B and C on the same side) give "equally close" |
| `order_nodes` | Puts lettered nodes in order, oldest to youngest | Without times: every order consistent with ancestry is accepted (nodes on different lineages cannot be ordered); the item states this in its key. With times: the one order by age (ties refused) |
| `select_true` | Selects all true statements | Statements are built from templates and each is engine-evaluated: "X and Y share a more recent common ancestor than X and Z", "{set} is a clade", "{set} is a clade in tree i but not in tree j", "trees i and j show the same relationships", "node P is older than node Q" (ancestry or times), "node P is older than {age}" and "lineage X is at least {age} old" (with times; a lineage is at least as old as its sister's oldest fossil tip), "X has trait T", "T is a shared derived trait of {set}", "T2 arose within a lineage that already had T1" |
| `trait` | "Which taxa have trait T?" (select-all); "Which trait is shared by exactly this clade?"; "How many times did T change?"; "Which states does X have?" (a tip's full trait profile, with authored names for ancestral and derived states); "Is T ancestral or derived in X?"; "Which tip has T1 but lacks T2?"; "Is T in X and Y homologous or did it arise independently?" | From marks: a tip has T if a gain lies on its path from the root and no later loss does; ancestral vs derived compares a tip's state with the root's; homologous if one gain lies on both tips' root paths, independent if separate gains; counts are the number of marks for T |
| `concept` | Multiple choice about what trees mean ("what do the lines represent?") | **Authored answer**, shown with an "authored answer" label in keys |
| `two_tier` | A computed question (any type above) plus "because…" reasons | Answer computed; the correct reason is **authored** and labelled |

Distractor notes (e.g. "looks most similar") are authored text attached to options, never answers.

### 4.4 Test mode
A set may declare `"mode": "test"` (forms A and B do). In test mode there is no Check, no feedback and
no retry; the student answers every item, then sees one summary (score and, per item, the engine
explanation). Practice is the default mode. v1.5's graded mode builds on test mode *(conductor's call:
the before form must not teach before the after form)*.

### 4.5 Drawing lengths and times
- Trees are drawn as **cladograms** by default: branch lengths, if present, are ignored and tips line
  up *(conductor's call: phylogram reading brings misconceptions the lessons don't teach)*.
- With `times`, the tree is drawn to the time axis: node positions come from ages; tips are at age 0
  unless a tip has its own age (an extinct or fossil taxon), drawn ending before the present.
  Branch lengths are then ignored; if both are present, `times` wins and the loader notes it.

### 4.6 Links and storage
Share links use `#r=` (compressed JSON, as `#x=` does). Files save as `.neophylo-reading.json`
*(conductor's call)*. Built-in sets live in `exercises/reading/`.

## 5. Engine (`crates/neophylo-core/src/reading/`)

### 5.1 Parsing and validation
Parse a reading set into a typed structure; resolve every clade identifier; check `times` decrease
toward tips and marks sit on existing branches; evaluate every item and refuse it with a
`NeoError` naming the item and field when its answer is not well defined (no unique differing tree,
`order_nodes` with tied ages, `closest_relative` with an empty answer, a `select_true` statement about
a taxon not in the tree, more than 4 trees, fewer than 3 or more than 40 tips per tree
*(conductor's call: 40)*). Never panics.

### 5.2 Queries
`mrca`, `is_clade`, `clade_of`, `sister_group`, `same_relationships` (rooted clade sets, polytomies
respected), `node_order` (ancestry partial order, or ages), `has_trait`, `shared_derived` and the
statement evaluator. Pure functions on the existing `Tree` type.

### 5.3 Answers
`answer(item) -> Answer` returns the accepted answer set plus a short engine-generated explanation
("A and B meet at node P; A and C meet at node Q, which is older") used by practice feedback and keys.
`check(item, response) -> Verdict` is exposed now for practice feedback and reused by the v1.5 grader.

### 5.4 Variant transforms
`rotate(tree, seed)`, `shuffle_tip_order(tree, seed)`, `relabel(set, pool, seed)`: deterministic for
a seed; answers of the transformed set are recomputed, never copied. Exposed to wasm but unused by
the UI in v1.4d.

### 5.5 Property tests and fuzzing
- Rotation and style invariance of every answer; relabelling equivariance.
- `mrca`, `is_clade` and `same_relationships` agree with brute force on random trees up to 12 tips.
- `order_nodes` accepted set = all linear extensions of the ancestry order (brute force ≤ 7 nodes).
- New strategies go in new proptest functions (saved seeds of existing ones stay valid).
- Fuzz target for the reading-set parser and the Newick-with-node-labels path: `Ok` or `NeoError`.

### 5.6 Oracle
R fixtures generated by a committed script with `ape::getMRCA`, `ape::is.monophyletic`,
`phangorn::RF.dist(rooted = TRUE)` / `ape::all.equal.phylo` and `ape::node.depth.edgelength`, over
the built-in sets and a random corpus; frozen in their own owner-gated PR, as for earlier oracles.
Trait membership, trait counts and the ancestry order have no `ape` function: the same R script
computes them independently with `ape::nodepath` (a separate implementation in another language),
and the Rust side is also checked by brute force (§5.5) *(conductor's call)*.

## 6. Tree drawing styles

- Shared layout in `web/src/layout/` gains pure functions for **diagonal** and **rooted circular**
  layouts, **tips right, up, left or down** orientation (mirrored pairs), slanted tip labels for
  tips-up diagonal trees, **node letters**, a **time axis** (numeric with unit and source, or schematic
  "older → younger" arrow), **trait marks** (a short bar across the branch with the trait name; gains
  and losses distinguished by shape, not colour alone) and polytomies.
- The reading area uses the new styles; the sandbox tree view and its exports are unchanged in v1.4d
  *(conductor's call)*.
- Text ≥ 12 px, nothing clipped or overlapping at 360, 768, 1,024 and 1,280 px widths in both themes;
  long organism names wrap or abbreviate by a rule the layout tests cover; trees keep natural height.
- Tap targets for nodes and tips ≥ 40×40 px (invisible hit areas), measured with `hasTouch`.
- Narrow screens *(conductor's call)*: below 600 px, multi-tree items stack trees vertically
  (labelled Tree 1…4) instead of side by side; tips-up trees are limited to 12 tips (validation
  refuses more), which fit at 360 px; any tree wider than its panel scrolls inside the panel with a
  visible scroll cue and never squeezes text below 12 px.

## 7. The Reading trees area

### 7.1 Entry points
A "Reading trees" item in the header and the library's "Tree reading" filter. `?read=<id>` opens a
built-in set; `#r=` opens a shared one. The area is lazy-loaded so the initial-JS budget does not grow.

### 7.2 Screen
One item at a time: the question, the tree(s), the answer control, then **Check**. Progress ("Question
3 of 10") and Back/Next. No matrices, stepper or settings. Presenter font sizes apply.

### 7.3 Interaction (tap or click only, no drag) *(conductor's call)*
- Select a node or tip by tapping it; multi-select by tapping several; a visible selection list with
  remove buttons.
- `order_nodes` uses tap-in-sequence with move-up/move-down buttons, not drag and drop.
- **Rotate tool** (available on every item unless the item disables it): tap a node, press "Rotate
  here", and its children swap with a short animation; teaches that rotation changes nothing.
- Keyboard: arrow keys move between nodes along the tree, Enter selects, R rotates; every control
  reachable by Tab.
- Screen readers: each tree also has a text description as nested groups ("Node P contains: whale,
  hippo"), and selection state is announced.

### 7.4 Practice feedback
After **Check**: correct or not, the engine explanation, and the item's `note_after`. A student can
retry. (v1.5 adds a graded mode with no feedback until the end.)

### 7.5 Editor reading mode
The editor gains "Tree reading set": paste Newick or draw a tree on the existing canvas, set letters,
times and marks by tapping nodes and branches, add items by type (tips and nodes chosen by tapping),
see the engine's answer and any validation error live, preview as a student, share a link, save a file.
No JSON editing.

## 8. Content

All content is NeoPhylo-written, follows the lesson-content rules (no spoilers before the student
acts, no hand-typed numbers that can mismatch, support never read as probability), and is an
owner-gated review.

### 8.1 Four reading lessons
1. **Reading a tree:** tips, branches, nodes, root, what lines and nodes mean, time direction.
2. **Rotation changes nothing:** same relationships drawn differently; tip order is not "more evolved".
3. **Who is closest?** Relatedness from shared ancestry, not tip proximity or resemblance.
4. **Clades and shared traits:** monophyly, trait marks, shared derived traits.

Real organisms with topologies taken from the Open Tree of Life synthesis (CC0) or a cited source;
times, where shown, cited from published estimates or drawn schematic. Avoid placements still
debated. Abstract letter-labelled trees are used where published instruments use them.
Provenance recorded per tree, as for the data library.

### 8.2 Before/after forms
Two parallel forms (A and B), 10–12 items each, the same misconception categories, different trees
and taxa, so a class can take one before and the other after. Both run in test mode (§4.4) and
also print as paper worksheets. Labelled "NeoPhylo's own questions,
not a validated instrument". The guide cites the published instruments (Baum et al. 2005; Naegle's
Tree-Thinking Concept Inventory; Kummer et al. 2019's Evolutionary Tree Concept Inventory) for
instructors who need validated measures.

### 8.3 Format coverage set
`exercises/reading/coverage/`: one or more NeoPhylo-written items per format found in the published
instruments, with a manifest naming the instrument and format each mirrors (citation only, no
wording or figures copied):
- several trees, "which shows a different relationship" with "all the same";
- time order of nodes, with and without a time axis, and "the diagram has no time component";
- closest and most distant relative of a named taxon or labelled node;
- relatedness versus resemblance distractors;
- meaning of lines and of nodes (concept items);
- true/false statements as select-all, including statements across two diagrams;
- "because…" two-tier items;
- MRCA location, clade membership, smallest clade;
- trait marks: which taxa have a trait, shared derived traits;
- every drawing style: rectangular, diagonal and rooted circular; tips right, up, left and down;
  lettered nodes and lettered points on branches; time axis; trait marks; polytomy; fossil tips;
- from Baum et al. 2005 (supplement, Quiz I and the tree-structure parts of Quiz II): pairwise
  relatedness with "equally related"; MRCA among lettered points on tips, branches and nodes; place a
  new taxon on a lettered branch; which smaller tree conflicts with a reference tree; which rotated
  or restyled tree differs; a tip's trait states from ancestral states and gain/loss marks; which tip
  has one trait and lacks another (with a loss and a trait arising twice); a clade in one tree but not
  the other; which tree fits a set of small rooted trees; order and number of gains of two traits;
  node and lineage ages against a date with fossil tips;
- from Kummer et al. 2019 (ETCI; formats inferred from its learning outcomes, since the items are
  available only from the authors): two-tier content-plus-reason items; mono-, para- and polyphyly of
  a trait-defined group; comparing relatedness; meaning of tree parts; rotation versus different
  relationships; homology versus independent origin; synapomorphies; ancestral versus derived state;
  which traits a taxon has; "primitive/advanced" and "living species still evolve" (concept items);
  counting clades.

**Known gaps, deferred (owner, 2026-11-18: parsimony and branch-length formats move to v2.0)** — listed
in the coverage manifest and the guide:
- which tree fits a character matrix, and character evidence for a group (parsimony, v2.0);
- branch lengths drawn to a scale bar, V-shaped unrooted trees with lengths (v1.8 drawing, v2.0);
- colour-mapped ancestral states, ambiguous branches, counting migrations (ancestral state
  reconstruction, v2.7);
- support values on branches and "how many branches would have to be wrong" (support is inferred
  data; v2.x);
- error bars on node ages and external event lines (dating, v2.6);
- similarity dendrogram versus phylogeny, comparing co-evolution trees, soft versus hard polytomy:
  kept as `concept` or `two_tier` items with authored answers, not computed. A test loads every coverage
item, renders it in each allowed style and checks the engine answer; an e2e test builds a sample of
them through the editor.

### 8.4 Library, worksheets, guide
- Reading sets appear in the library as "Tree reading" cards with level, minutes and objectives.
- **Paper worksheet** for every built-in set: trees drawn in their style (light print styles), each
  question with answer space. **Answer key** behind the existing "I'm an instructor" step, every
  answer computed at render time, with engine explanations; authored answers labelled.
- Instructor guide: a "Teaching tree reading" section, a 50-minute tree-reading class plan, how to use
  forms A and B, how to build a reading set in the editor, and a **measuring learning** section with
  citations (Baum et al. 2005; Kummer et al. 2019; Furrow & Hsu 2019's review of evolution concept
  inventories) and these caveats: NeoPhylo's items are new and not validated, so scores cannot be
  compared with published results; a subset or reordering of any validated instrument loses its
  validity evidence; multiple-choice guessing inflates single scores, so compare before and after;
  students do better on familiar than unfamiliar taxa, and trait loss is harder than gain, so the
  forms mix both; some instruments are available only from their authors (the ETCI) or carry no
  reuse licence (Baum's supplement reuses publishers' figures): cite them, and ask the authors before
  typing their items into NeoPhylo.

## 9. Testing

- **Engine:** oracle parity (§5.6), property tests and fuzzing (§5.5), `NeoError` tests for every
  refusal in §5.1. Existing tests unmodified.
- **Schema:** valid examples load; each refusal returns the right message; exercise-format files are
  unaffected.
- **Web:** Vitest for layout functions (each style, long names, polytomies), reading state and `#r=`
  links. Playwright for every question type by mouse, keyboard and touch (CDP touch events, since
  `pointerup` targets are wrong for touch), the rotate tool, practice feedback, editor reading mode,
  library filter, worksheet and key.
- **Accessibility:** axe on every new view; a manual keyboard and screen-reader pass over one set.
- **Visual:** snapshots of each style, each question type, the editor reading mode, a worksheet and a
  key, both themes, standard widths, print views in light paper; baselines owner-approved.
- **Content:** a test that every built-in item's engine answer matches the answer the author expects
  (stored as an expectation in the test, not in the content file), so a content edit that silently
  changes an answer fails.

## 12. Risks
- **Ordering answers are subtler than they look:** nodes on different lineages have no order without
  times. Mitigated by accepting every consistent order and saying so in keys.
- **"Closest relative" has several right answers** when the sister group has more than one tip.
  Mitigated by computing the accepted set and offering select-all wording.
- **Real-organism trees can be contested.** Mitigated by cited sources and avoiding debated
  placements.
- **Touch interaction bugs** (known from v1.4). Mitigated by tap-only interaction and CDP touch tests.
- **The new area drifts from the design system.** Mitigated by reusing components and the same
  visual QA set.
- **Review load** from four lessons, two forms and the coverage set. Mitigated by scheduling reviews
  per item.
