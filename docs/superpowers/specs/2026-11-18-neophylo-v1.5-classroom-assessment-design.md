# NeoPhylo v1.5: classroom delivery and assessment, design spec

Status: Draft for owner review · Date: 2026-11-18 · Repo path: `docs/superpowers/specs/2026-11-18-neophylo-v1.5-classroom-assessment-design.md`
Builds on the v1–v1.4d specs (v1.4d, tree reading, ships first). Roadmap entry: `docs/roadmap.md` § v1.5
(🟡 early-adopter pilot point). Market check behind it: `docs/market/2026-11-18-market-and-viability.md`.

## 1. Purpose and decision record

v1.5 makes NeoPhylo **instructor-ready**: an instructor gives a NeoPhylo assignment through their LMS,
each student gets their own variant, and the instructor grades the whole class from the LMS export,
with no accounts and no server. The owner starts outreach after v1.5.

**Why (owner, 2026-11-18):** outreach waits until an instructor can run a real lab or tree-reading
session and grade it. The market check found that the tools that grade phylogenetics work (Labster,
LearnSci, SimBio) are paid and per-student, and that AI use on homework is driving demand for
per-student variants. Free auto-checked variants with bulk grading and a published accessibility
report are NeoPhylo's strongest differentiator.

**Decisions (owner, brainstorming 2026-11-18):**
- **Completion codes carry the student's own answers** (option B): the instructor's grader rebuilds
  that student's variant and grades it. A copied code fails; a forged passing code means computing the
  right answers. Answer keys are hidden for assignment links.
- **Bulk grading:** the instructor drops the LMS's exported submissions (CSV) on an offline Grade page
  and gets every student's score, per-question results, common wrong answers, flags and a gradebook
  CSV to import back.
- **Variants come from a student-typed ID** (option A): the student types the ID the assignment asks
  for (e.g. university email); the variant comes from that ID plus the assignment; the grader matches
  the ID against the LMS row.
- **Attempts (option A):** the code records each task's **first attempt and final answer**. The
  instructor chooses at assignment time only whether students see feedback (practice) or not (test),
  and chooses the scoring rule later on the Grade page.
- **Architecture: an assignment is a small wrapper** around existing content (approach 1, §3); grading
  runs in the Rust engine; the Grade page reads CSVs and shows results.

**Calls made by the conductor (owner may overrule while reviewing):** marked *(conductor's call)*.
- Presenter mode is dropped from v1.5: it shipped in v1.3.
- The "offline lab pack" is replaced by a guide note on preloading lab machines: the app already works
  offline after the first visit.

**Success criteria:**
1. For every built-in lesson, lab and reading set that can be assigned, and for 1,000 generated
   student IDs each: the variant is deterministic, satisfies the content's declared premises (§5.2),
   and a simulated student who answers every task correctly scores 100%; changing any one answer
   lowers the score for exactly that task.
2. A code decodes to exactly what was encoded (property test); a code with any single character
   changed is rejected by its checksum; a code from another ID or another assignment is flagged.
3. The Grade page grades a 300-student synthetic export in each supported format (§8.2) in under
   10 seconds on a typical laptop (60 seconds when bootstrap tasks are graded, in a worker with
   progress) and produces a gradebook CSV matching the LMS's documented import format.
4. The full loop runs end to end in Playwright: build an assignment, 30 synthetic students take it
   (practice and test), their codes go into a CSV, the Grade page grades it, the gradebook matches
   the expected scores.
5. An embedded assignment works inside an iframe with third-party storage blocked.
6. A WCAG 2.1 AA self-audit of every view (embed mode included) finds no open failures, and an
   Accessibility Conformance Report (VPAT, WCAG edition) is published.
7. All existing engine, parity, lesson-premise and old-link tests pass unmodified. No existing number
   changes.

## 2. Scope

### 2.1 In v1.5
- Engine: assignment model, variant generation with premise checks, task answers and checking
  (including tie-aware `predict_pair` and numeric tasks), completion-code encoding, grading (§5).
- Assignment wrapper format and `#a=` links; an assignment builder in the editor (§6).
- Student flow: ID entry, practice and test modes, Finish and code, embed mode (§7).
- Grade page: CSV adapters, column mapping, scoring rules, results, flags, exports (§8).
- Per-lesson and per-assignment "copy assignment text" for the LMS (§7.5).
- Carried over: editor autosave, lab print fit, the checkpoint bootstrap binomial bound (§9).
- Accessibility: WCAG 2.1 AA self-audit and published ACR/VPAT (§10).
- Instructor guide: running an assignment, grading, privacy, the limits of no-account grading.

### 2.2 Non-goals
- Accounts, a server, LTI 1.3 or grade passback (v3.0).
- Enforcing a single attempt or a time limit: impossible without a server; the code records attempts
  and timestamps instead.
- Grading written answers: written prompts stay in the assignment but are collected in the LMS, not
  in the code *(conductor's call: keeps codes short)*.
- Preventing a determined student from computing answers with the app itself (§11).
- Question banks and more task types across modules (v2.5); misconception maps across sections and
  terms (v3.1). v1.5's "common wrong answers" covers one class and one assignment.
- An independent accessibility audit (v3.2).

## 3. Approaches considered

1. **An assignment is a small wrapper** *(chosen)* that points at a built-in lesson or reading set or
   carries an editor exercise, plus settings (practice/test, ID prompt, graded tasks), shared as
   `#a=`. Grading runs in the engine; the Grade page reads CSVs and shows results. Existing lessons,
   formats and links are untouched.
2. **Put assignment settings inside the exercise and reading formats.** One fewer file type, but every
   existing lesson's format changes and the old-link corpora are at risk. Rejected.
3. **A separate downloadable grader file.** Grading survives the site going away, but it is a second
   build to maintain. Rejected; the Grade page works offline like the rest of the app.

## 4. Assignment format

JSON validated by `exercises/assignment.schema.json`, `schema_version: 1`, `kind: "assignment"`:
- `id` (random, generated by the builder), `title`, `instructions` (optional text shown first).
- `content`: one of `{ builtin: "<lesson, lab or reading-set id>", content_hash: "<hash>" }`,
  `{ exercise: <exercise file> }` or `{ reading: <reading-set file> }`. Production serves only the
  latest release, so a built-in reference records a hash of the content file: if a later release
  changed that content, the student flow shows a notice and the grader flags every row "content
  changed since the assignment was made" instead of grading silently. A repo test fails when a
  release changes a built-in file's answers without a changelog entry naming it *(conductor's call)*.
- `id_prompt`: the label students see and a normalisation rule (trim + lowercase by default). The
  builder offers presets that match what each LMS export contains: Canvas "Student number (SIS ID)",
  Moodle "ID number" or "Email address", Forms "Email address" (when the form collects emails), or
  a custom label *(conductor's call)*.
- `mode`: `practice` (feedback after each task, retries allowed) or `test` (no feedback until Finish,
  then a summary).
- `tasks`: which items are graded (§5.3), each with optional points (default 1).
- `variation`: on or off (off = everyone gets the same exercise, still graded).
- Shared as `#a=` (compressed, like `#x=` and `#r=`); saved as `.neophylo-assignment.json`.

## 5. Engine (`crates/neophylo-core/src/assess/`)

### 5.1 Variant seed
`seed = hash(assignment.id, normalise(student_id))`, a fixed, documented, platform-independent hash.
Same ID and assignment always give the same variant.

### 5.2 Variants per content kind
- **Simulated exercises** (true tree + simulation): the seed drives the simulation; tips are relabelled
  from the exercise's taxa and the tree rotated.
- **Matrix exercises derived from a tree** (editor "derive"): a seeded random tree with the same
  number of taxa, its additive matrix, rounded as the author set.
- **Fixed-data exercises** (real alignments, typed matrices): data cannot vary; variation is limited to
  the bootstrap seed. The builder warns "every student gets the same data" *(conductor's call)*.
- **Reading sets:** the v1.4d transforms (rotate, shuffle tip order, relabel from `taxa_pool`).
- **Premises:** content may declare machine-checkable premises (`tie_free`, `closest_pair_not_first`,
  `upgma_differs_from_nj`, `nj_recovers_true_tree`, and the reading-set validity rules). The generator
  retries with derived seeds (`seed`, then `hash(seed, k)` for k = 1…50) until every premise holds;
  if none does, it falls back to the base exercise and the builder reports it at authoring time.
  Built-in lessons gain premise declarations matching what their existing premise tests assert.

### 5.3 Gradable tasks
Every task's answer is computed from the student's variant; targets are defined by **role**, never by
taxon name, because names vary ("the pair joined at step 2", "the closest pair at step 3").
- `predict_pair` (existing prompt type): accepts every pair tied at the minimum when the engine reports
  a tie, including `tie_same_split` (deferred from v1.4c Task 10).
- `predict_branch` (existing): the least-supported group from the variant's seeded bootstrap run.
- Numeric tasks: `q_value`, `branch_length`, `new_distance`, `corrected_distance` at a step for a pair
  given by role. Correct when the student's number rounds to the engine's value at the precision the
  app displays for that quantity *(conductor's call: never a hand-set tolerance)*.
- Every v1.4d reading-set type. `concept` and `two_tier` reasons use their authored answers.
- `check(task, response) -> Verdict` is the same function the practice feedback uses.

### 5.4 Completion code
- Contents: format version, variant-generator version (§5.7), assignment fingerprint (short hash of
  the assignment file), **the normalised student ID**, variant retry index, per task (first answer,
  final answer only if it differs, attempts count), Finish timestamp (minutes), checksum.
- The ID is carried in the code so the grader can always rebuild the variant, even when the LMS export
  lacks that column; the code is only ever pasted into the LMS, which already knows the student
  *(conductor's call, after the builder check: Canvas quiz exports may not contain the email or login
  a student typed)*. When the export does contain a matching column, the grader cross-checks it;
  the same code submitted by two students is flagged whether or not it does.
- Answers are packed compactly (pair as two tip indices, select-all as a bitmask, orders as a
  permutation index, numbers as scaled integers at display precision).
- Text form: Crockford base32, prefix `NP1-`, grouped by 5. At most 15 graded tasks per assignment;
  the builder computes the worst-case code length and refuses settings that exceed 250 characters
  *(conductor's call)*.
- Decoding never panics; malformed codes return `NeoError` with a reason.

### 5.5 Grading
`grade(assignment, student_id, code, rule) -> Result` rebuilds the variant, checks each recorded
answer and returns per-task verdicts and the score under the chosen rule:
`first` (first attempt only), `final` (final answer only) or `weighted` (full points if first attempt
correct, a set fraction if only the final is, default 0.5). Flags: ID mismatch, assignment mismatch,
content changed, checksum failure.

### 5.6 Graded tasks inside step-by-step lessons
The step-through view shows answers as it goes (a join reveals the joined pair; the matrix and
explanation panels show Q-values, branch lengths and distances). In an assignment:
- The stepper cannot pass a graded task until it is answered. Advancing past it **commits** the answer:
  in both modes it cannot be changed afterwards.
- Practice mode: before committing, the student may check and retry (each check is an attempt; the
  first and final answers are recorded). Test mode: one answer, no right/wrong mark; the join itself
  then appears as usual, which is not graded feedback.
- Numeric tasks are worked by hand: the quantity asked for (and the panels that would show it for that
  step) stays hidden until the task is committed; the inputs needed (the current distance matrix) stay
  visible *(conductor's call)*.
- Bootstrap tasks (`predict_branch`) fix the bootstrap settings in the assignment (replicates ≤ 200,
  alignment length, seed from the variant); the controls are locked so the grader reproduces the run.
- Built-in lessons without gradable prompts (e.g. `saturation`, `upgma-fails`, `upgma-vs-nj-matrix`)
  are assignable once the instructor adds numeric or prediction tasks by role in the builder; v1.5
  does not edit lesson content. Labs use fixed data, so every student gets the same answers, and the
  builder says so.

### 5.7 Stability across releases
The variant generator has a version carried in every code. Golden tests pin the variants (data and
every task answer) for a corpus of assignments and IDs; they are treated like fixtures: changing them
is an owner-gated change and requires a new generator version, with the old version kept in the
engine so codes made under it still grade *(conductor's call)*.

### 5.8 Testing
Property tests (§1 criteria 1–2), golden variant tests (§5.7), brute-force checks of tie acceptance, fuzz targets for the code
decoder. New strategies in new proptest functions.

## 6. Assignment builder (editor)

"Make an assignment" from any library card or from the editor: choose content, mode, ID prompt and
graded tasks (prompts and items listed with their engine answers on the base variant; numeric tasks
added by picking step, quantity and role), turn variation on or off, preview as three sample students
side by side, then copy the link or the LMS text. Premise failures and "same data for everyone"
warnings show here. The builder autosaves its draft (§9.1).

## 7. Student flow

### 7.1 Start
An `#a=` link shows the title, instructions and the ID prompt. The ID is asked once; the variant
appears. A "Not you? Change ID" link restarts.

### 7.2 Working
The lesson or reading set runs as today with graded tasks marked. Practice mode gives feedback and
retries; test mode gives none until Finish. Answer-key links and the "I'm an instructor" step are not
offered inside an assignment. Progress is saved in local storage (every access in try/catch); if
storage is blocked, the page says so and progress lasts only while the tab is open.

### 7.3 Finish
Finish shows the score (practice) or the summary (test, §4.4 of v1.4d) and the code with a Copy
button and the instruction "Paste this code into <LMS place> as your answer". The code stays
retrievable from the same browser.

### 7.4 Embed mode
`?embed` (also set automatically when framed): no header or library chrome, an "Open in a new tab"
link, works with third-party storage blocked. Production headers allow framing by any site
(`frame-ancestors *`) *(conductor's call: LMS domains vary per institution)*.

### 7.5 Copy assignment text
Every library card and every assignment offers LMS-ready text (plain and HTML): what to do, the link,
the ID to type, where to paste the code.

## 8. Grade page (`?grade`)

### 8.1 Flow
Open the assignment (link or file), drop the submissions CSV, confirm the detected ID and code
columns (auto-detected; codes found by their `NP1-` prefix in any cell), pick the scoring rule, see
results. Lazy-loaded; works offline; nothing leaves the browser.

### 8.2 Supported inputs
Canvas quiz "Student Analysis" CSV (Classic and New Quizzes), Moodle quiz responses CSV, Google Forms CSV, Microsoft Forms
(saved as CSV) and any CSV via manual column mapping. Several codes for one student: the latest
Finish timestamp counts and the others are listed.

### 8.3 Results and exports
- Per student: score, per-task verdicts, flags (ID mismatch, same code from two students, wrong
  assignment or changed content, invalid code, missing code).
- Per task: percent correct (first and final), the three most common wrong answers.
- Exports: a plain results CSV, and "fill my gradebook": the instructor drops their Canvas or Moodle
  gradebook export and gets it back with the assignment column filled, ready to import.

### 8.4 Privacy
Student data stays in the instructor's browser; nothing is uploaded or stored after the tab closes.
The guide says so in one paragraph suitable for an institution's review.

## 9. Carried-over items

### 9.1 Editor autosave
The unsaved editor draft (including a matrix draft, a reading-set draft and an assignment draft)
survives a reload; local storage, every access in try/catch (deferred from v1.4c Task 9).

### 9.2 Lab print fit
Lab-page trees use the v1.4c printable-width refit (`printFit`) so very wide lab figures never print
text under 12 px (deferred from v1.4c, owner 2026-11-17).

### 9.3 Checkpoint bootstrap bound
`mega_verify.py --boot` replaces the flat 5 pp limit with a per-split binomial bound; **the owner
approves the number** (deferred from v1.4c, owner 2026-11-18).

## 10. Accessibility conformance
A WCAG 2.1 AA self-audit: the existing axe checks plus a manual keyboard and screen-reader pass
(NVDA + Firefox, VoiceOver + Safari) over every view, embed mode, the assignment flow and the Grade
page. **The owner runs the screen-reader passes** in a Windows VM and, if needed, a macOS VM, from a
written script the plan provides (owner, 2026-11-18). Failures found are fixed in v1.5; anything not
fixed by the release checkpoint is listed in the report as a known issue with a planned fix
*(conductor's call)*. The owner signs off the audit log and the report (owner gate). An Accessibility Conformance Report on the VPAT 2.x WCAG edition
template is published in the repo and linked from the site footer and guide. US public universities
must meet WCAG 2.1 AA under ADA Title II by 2027-04-26.

## 11. Honesty limits (stated in the guide)
- Codes stop casual copying between students and make forging require the right answers. They do not
  stop a student who works the variant out with the app's own sandbox, or who reloads to retry in test
  mode (the attempts count records reloads only on the same browser).
- Fingerprints are short hashes: collisions are possible but rare; the grader shows the flag, never
  silently accepts.

## 12. Testing
- **Engine:** §5.8 plus premise-generator tests for every built-in assignable content.
- **Real LMS (owner, 2026-11-18: no institutional LMS available):** a local Moodle in Docker
  (official `moodlehq` images) runs the full loop for real: assignment link in a page and in an
  iframe, quiz submissions from test students, quiz responses export, Grade page, gradebook import
  back into Moodle. A local Canvas (the open-source `canvas-lms` Docker setup) does the same if it can
  be brought up within one day of effort; otherwise Canvas is checked against its documented formats
  and a real Canvas export is the first thing asked of a pilot instructor *(conductor's call)*. The
  exports captured from these instances become the adapter fixtures. The LMS containers run on the
  conductor's machine only, never in CI.
- **Web:** Vitest for CSV adapters (fixture files captured from the local LMS instances, or modelled
  on each LMS's documented export), column
  detection, scoring rules and flags; Playwright for the builder, the student flow in both modes,
  embed mode in an iframe with storage blocked, the Grade page and the full loop (§1 criterion 4),
  touch and keyboard paths.
- **Performance:** the 300-student grading budget (§1 criterion 3) as a `@perf` test.
- **Visual:** builder, student start, Finish, Grade results, embed mode; both themes, standard
  widths; baselines owner-approved.
- **Accessibility:** axe on every new view; the manual audit log is committed with the ACR.

## 15. Risks
- **LMS export formats change or differ by institution.** Mitigated by manual column mapping as the
  fallback for any CSV and by `NP1-` prefix detection.
- **Variants break a lesson's teaching point** (e.g. a tie appears). Mitigated by declared premises,
  the retry loop and the builder's authoring-time report.
- **Students mistype their ID.** Mitigated by the ID-mismatch flag with the typed fingerprint shown,
  so the instructor can match by hand.
- **Built-in content changes after an assignment is made.** Mitigated by the content hash flag and
  the changelog test.
- **Instructors mistake codes for proctoring.** Mitigated by the honesty-limits section of the guide.
