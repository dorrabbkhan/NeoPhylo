# NeoPhylo v1.4: Instructor kit and PHYLIP lab packs, design spec

Status: Approved for planning · Date: 2026-10-26 · Repo path: `docs/superpowers/specs/2026-10-26-neophylo-v1.4-instructor-kit-design.md`
Builds on the v1, v1.1, v1.2 and v1.3 specs. Roadmap entry: `docs/roadmap.md` § v1.4 (split: this spec is v1.4; the MEGA companion and data library move to **v1.4b**, which gets its own spec).

## 1. Purpose and decision record

v1.4 lets an instructor build and share their own exercises without editing JSON, and gives PHYLIP teachers a ready-made replacement for their classic labs. It adds two DNA models so NeoPhylo reproduces `dnadist`'s numbers, and it keeps the existing K80 unchanged.

**Decisions (owner, brainstorming 2026-10-26):**
- **Split:** v1.4 = PHYLIP parity models + PHYLIP lab packs + exercise editor. v1.4b = MEGA companion, `.meg` import, MEGA-CC as oracle, curated data library.
- **Exercise persistence:** the exercise JSON file is the source of truth. The shareable `#x=` link is generated from it. Import accepts either.
- **PHYLIP K2P is a separate model** with a clear name and a note on screen. K80 is not changed or renamed.
- **Identifiers:** JSON names are `F84` and `K2P_PHYLIP`, following the uppercase convention of `JC69`, `K80` and `JTT`. The uppercase form also avoids the existing `"Kimura"` name, which already means the protein correction.
- **Base frequencies:** the instructor sets A, C, G and T frequencies in the editor for F84 simulation, with equal frequencies as the default. Estimation uses observed frequencies, as `dnadist` does by default.
- **Lab packs** are in-app pages with a print view, not separate PDF or Word files.
- **Editor tree input:** drag-to-draw, Newick text and a branch-length table, side by side. All three are views of one tree model.
- **Drag-to-draw stays in v1.4.** The schedule is not tight, so it is not deferred.

**Success criteria:**
1. `F84` and `K2P_PHYLIP` distances match `dnadist`'s printed output on committed fixtures.
2. Every PHYLIP lab pack reproduces its PHYLIP chain's numbers with the settings the pack lists.
3. An instructor can build an exercise in the editor, save it as a file, reload it, share a link, and have a student complete it, with no JSON editing.
4. Every exercise the editor produces validates against `exercises/schema.json`.
5. All existing engine, parity, lesson-premise and old-link tests pass unmodified. No existing number changes.

## 2. Scope

### 2.1 In v1.4
- Two new DNA models in the engine: `F84` and `K2P_PHYLIP` (with a user-set ratio).
- Simulation under `F84`, with base frequencies set by the instructor in the editor (default equal), so the editor can generate data from a true tree. Simulation under `K2P_PHYLIP` reuses the existing K80{κ} simulator with κ set to the ratio.
- Exercise editor: tree input (drag, Newick, table), model/seed/length settings, base frequencies for F84, prompts, preview, save and import as JSON, share link.
- PHYLIP lab packs: three chains, each with a handout, matching settings, the "what PHYLIP's outfile showed you vs what NeoPhylo shows you" note, and a print view.
- A lab index page listing the packs and their objectives.
- Lessons and tests for every new screen and model.

### 2.2 Non-goals
- MEGA companion, `.meg` import, MEGA-CC oracle, curated data library (v1.4b).
- Accounts, grading, completion codes, randomized variants (v1.5).
- Printable worksheets with answer keys and the instructor guide. These are planned as part of the lesson-library work and will be scoped in the plan if they fit, otherwise moved to v1.5. (Open item, §9.)
- Likelihood, Tamura-Nei, LogDet, gamma (v1.7 and later).
- Estimating base frequencies from data for F84 (the estimator uses observed frequencies, as in `dnadist`; the instructor-set frequencies apply only to simulation).
- Any change to existing distances, trees, bootstrap, simulation or lesson results.

## 3. Engine: models and parity

### 3.1 Models
- **`F84`:** the F84 distance, the default model of PHYLIP `dnadist`. Its parameterization follows the definition used by `dnadist`, so the fixtures are the reference, not the formula in this spec. Estimation uses observed base frequencies, as `dnadist` does by default. The plan shows the derivation in a step-level worked example.
- **`K2P_PHYLIP`:** the Kimura 2-parameter estimator as `dnadist` computes it, with transition/transversion ratio `κ` set by the user (default 2.0). Its distance is a different estimator from K80's closed form, and the spec keeps the divergence explicit (§3.3).
- **`K80`:** unchanged. Still validated against ape.
- Both new models return `Saturated` cells under the same rules as existing models (§4.2 of the v1 spec). The engine never panics on any input.
- Both are pure Rust, use `libm` for all math, and follow the determinism rules in `docs/architecture.md`.

### 3.2 Parity validation
- New fixtures are generated by `fixtures/generate_phylip.sh` with `dnadist` and `neighbor`, and committed in a commit separate from engine code (CI's fixture guard). The generator's `dnadist` and `neighbor` versions are recorded with the fixtures.
- Tolerance: match `dnadist`'s printed precision for each fixture. The plan confirms the exact printed precision from the generator's output and records it in the fixture README. No tolerance is loosened to make a test pass.
- NJ trees for PHYLIP-chain fixtures are compared using PHYLIP's own printed distance matrix as input, as the v1 spec does.

### 3.3 Known divergence
`K2P_PHYLIP` and `K80` will disagree on the same data, by design. The corpus test asserts this divergence rather than equality, and a property test asserts that the two agree when the ratio is set so that the models coincide, if such a case exists in the plan's analysis. Students see the difference in the UI (§6.4), not only in tests.

### 3.4 Property tests
- Both new distance matrices are symmetric with zero diagonal.
- Distances are non-negative and monotone in observed divergence on a fixed sequence pair.
- `K2P_PHYLIP` distances are finite for `κ > 0`; invalid `κ` (≤ 0, non-finite) is a `NeoError`, not a panic.
- F84 with equal base frequencies and no transition/transversion asymmetry is checked against its closed form in a worked example.

### 3.5 Simulation
- `sim` gains an `F84` option with base frequencies A, C, G, T supplied by the caller. They must be positive and sum to 1 within 1e-6; otherwise the call returns `NeoError`. The default is equal frequencies (0.25 each).
- It follows the existing fixed consumption order (root sequence first, then branches in preorder, one uniform draw per site per branch), so the golden-hash rule applies and new golden hashes are committed for seeded `F84` alignments, at the default frequencies and at one non-equal set.
- Convergence check: at 100,000 sites with default equal frequencies, the corrected F84 distance is within 2% of the true path length, as for the existing models.

## 4. Exercise format

- The exercise file is the existing lesson JSON, validated against `exercises/schema.json`. v1.4 adds the identifiers `F84` and `K2P_PHYLIP`, an `analysis.kappa` field (required for `K2P_PHYLIP`, default 2.0 in the editor), and an optional `sim.base_freqs` object for `F84` (A, C, G, T; default equal). No existing field becomes required.
- `schema_version` increments from 2 to 3 for the new fields. Old files load unchanged; the existing migration path handles them.
- Optional metadata the editor writes: title, short description, and an author name as free text. No accounts, no user identifiers.
- Prompts use the existing prompt types and gating (`PromptCard`). The editor offers only the types that already exist. New prompt types are out of scope.

## 5. Exercise editor

### 5.1 One tree model, three views
- The tree is held in one model. The drag canvas, the Newick text and the branch-length table all render from it, and each edit goes through the model.
- **Structural edits run in the engine.** Creating a node, joining two subtrees, moving a node, and setting a branch length are operations in `crates/neophylo-core`, with tests. The TypeScript layer only translates pointer and keyboard input into those operations and draws coordinates from the existing pure `layout` functions. No tree logic is duplicated in TypeScript.
- Invalid edits are refused with a message that says why (for example, a negative branch length, a duplicate taxon name, or a non-binary join where the model requires one). Negative lengths are not allowed in an editor-built exercise; the existing `TeachingNotices` display remains for loaded data.
- **Undo and redo** cover all structural edits and length edits.

### 5.2 Drag-to-draw
- Create a leaf, drag a leaf onto a branch to join it, drag an internal node to move it, and drag a branch end to change its length.
- Every drag action has a keyboard path: the table and Newick views are full keyboard alternatives, and keyboard shortcuts cover create, join and nudge. No function is available only by dragging.
- Touch targets are at least 40×40 px, as set in v1.3.

### 5.3 Settings and preview
- Model (`JC69`, `K80`, `F84`, `K2P_PHYLIP`, or the protein models already in the app), κ where it applies, seed, and sequence length.
- For `F84`, four base-frequency inputs (A, C, G, T), defaulting to 0.25 each. They must sum to 1; the editor shows the current sum and refuses to save until it is 1.
- A preview runs the same lesson player a student sees, so the instructor previews the real exercise.
- Prompts are added and ordered in a prompt list; each prompt is previewed with its gate.

### 5.4 Save, import and share
- **Save:** downloads the exercise JSON file, validated against the schema before download. A file that fails validation is not downloaded; the editor shows the first failing field.
- **Import:** accepts a JSON file or a `#x=` link. Both go through the same validation and migration path.
- **Share link:** generated from the saved file's content as the existing `#x=` format. If the encoded link is longer than the limit set in the plan, the editor says so and recommends sharing the file instead. The limit is set in the plan from the existing link format, not guessed here.
- The editor stores nothing on a server. Drafts in progress may use per-device storage for convenience only, wrapped in try/catch and never required to restore work.

### 5.5 Accessibility and layout
- Views reflow under the v1.3 breakpoints. Below 1,024 px, the table and Newick views open as full-screen sheets, as the pair and replicate panels do.
- Focus order, labels and live regions follow the existing WAI-ARIA patterns in `MatrixHeatmap`.

## 6. PHYLIP lab packs

### 6.1 Packs
Three packs, mirroring the classic PHYLIP chains named in the roadmap:
1. `dnadist` → `neighbor` (DNA distances, NJ)
2. `protdist` → `neighbor` (protein distances, NJ)
3. `seqboot` → `dnadist` → `neighbor` → `consense` (bootstrap-style replicates, consensus)

Pack 3 uses the bootstrap features shipped in v1.2. Its "seqboot" step is NeoPhylo's existing resampling, with the replicate count set to PHYLIP's default, which the plan confirms against the generator.

### 6.2 Contents of each pack
- An in-app lab page: objectives, handout text, and a "load this lab" button that loads the dataset and sets the matching model, seed and replicate settings.
- A settings table listing the PHYLIP default for each option and the matching NeoPhylo setting.
- The "what PHYLIP's outfile showed you vs what NeoPhylo shows you" note.
- A print stylesheet built on the v1.3 tokens, so the page prints cleanly in light colors.
- A link to the matching exercise file, so an instructor can copy or adapt it in the editor.

### 6.3 Datasets
- Each pack's sequences are either original or openly licensed. Provenance and license are recorded in the pack's data note, and in `THIRD_PARTY_NOTICES.md` where needed.
- Every pack's expected numbers come from committed PHYLIP fixtures, not from NeoPhylo's own output.

### 6.4 Review
- The "PHYLIP showed you" notes and handouts are reviewed for accuracy by a phylogeneticist reviewer before release. This is an **owner gate** under the conductor rules, not an automated check.
- Lesson content follows the existing lesson checks: no spoilers before the student acts, no hard-coded numbers that can mismatch.

### 6.5 Lab index
A page listing the three packs with their objectives, time estimates, and the settings each uses. Linked from the header and from "Coming from PHYLIP?"

## 7. Testing

- **Engine:** parity tests against new `dnadist` fixtures (§3.2); property tests (§3.4); simulator convergence and golden hashes (§3.5); `NeoError` tests for invalid `κ` and invalid base frequencies; the fuzzing of parsers is extended to cover the new exercise fields.
- **Editor model:** unit tests for every structural operation in the engine, including the refusal cases in §5.1.
- **Round trip:** an editor-built tree survives Newick → model → Newick and JSON → model → JSON with no change.
- **Schema:** every committed example exercise produced by the editor validates; a deliberately broken file is refused with the right message.
- **Web:** Vitest for editor state and view sync; Playwright for drag-to-draw with the keyboard-only path, save and reload, share-link round trip, and each lab pack's "load this lab" button.
- **Visual:** snapshot tests of the editor in both themes at 768, 1,024 and 1,280 px, and of each lab page's print view. Baselines are owner-approved.
- **Old links:** the v1.1–v1.3 link corpora restore identically.
- **Accessibility:** axe checks on the editor and lab pages.

## 8. Milestones inside v1.4

The plan will order the work so each step is testable on its own. Proposed order, to be confirmed in the plan:
1. Engine: `F84` and `K2P_PHYLIP` distances, fixtures, parity tests.
2. Engine: `F84` simulation with base frequencies, golden hashes.
3. Engine: tree editing operations, with tests.
4. Exercise format: new fields, `schema_version`, migration tests.
5. Editor: Newick and table views on the shared model, save/import/share.
6. Editor: drag-to-draw on the same model, with the keyboard path.
7. Lab packs: pack 1, then 2, then 3, each with its owner-gated review.
8. Lab index, print views, screenshots for UI PRs.

## 9. Open items for the plan
These are not blockers for this spec. Each gets an answer in the implementation plan:
- Whether printable worksheets with answer keys and the instructor guide fit in v1.4 or move to v1.5.
- The exact share-link length limit (§5.4).
- The exact printed precision for each parity fixture (§3.2) and the PHYLIP replicate default (§6.1).
- The datasets for each pack, with provenance (§6.3).
- Whether `K2P_PHYLIP` at a particular ratio can be shown to coincide with K80, which would make a useful property test (§3.3). If no such case exists, the test is dropped.

## 10. Risks
- **Editor size.** Drag-to-draw is the largest UI piece in the plan. Mitigated by building the Newick and table views first (§8) and by keeping all structure in the engine, so the drag layer stays thin.
- **Naming confusion** between `K80` and `K2P_PHYLIP`. Mitigated by distinct names, a visible note, and tests that assert the divergence (§3.3).
- **Parity surprises** in `dnadist`'s F84 conventions. Mitigated by fixture-first development: the fixtures are generated before the formula is trusted.
- **Review load** from three owner-gated lab packs. Mitigated by scheduling the reviews per pack, not all at the end.
